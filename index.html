# Office Administration Management System ## Production-Ready PostgreSQL Database Design (Version 1.0) **Prepared by:** Senior Database Architect **Platform:** PostgreSQL via Supabase (Auth, Storage, RLS) **Scope:** Complete relational schema for all 14 Version 1 modules **Format note:** No SQL syntax and no application code included, per instructions — all types, constraints, and rules are described in structured prose/tables. SQL implementation is reserved for the build phase. **Status:** Draft for Approval --- ## 1. Database Design Philosophy 1. **Office-scoped from day one.** Every table carries an `office_id`, even though V1 operates a single office. This makes multi-branch expansion a data change, not a schema change. 2. **Full audit trail by default.** Every major table carries `created_at`, `updated_at`, `created_by`, `updated_by`, and a `status` where applicable, satisfying the audit requirement without needing per-table history tables. 3. **Data-driven over hardcoded.** Statuses, roles, permissions, and asset/document categories live in lookup tables rather than fixed code lists, so the business can extend them without a migration. 4. **One reusable engine per cross-cutting concern.** Approvals, audit logging, and notifications are each modeled once as generic, polymorphic engines — reused by every module, present and future — rather than rebuilt per module. 5. **UUID primary keys throughout.** Matches Supabase Auth's UUID user identifiers, avoids enumeration risk, and supports safe multi-office/multi-environment merges later. 6. **RLS is a first-class design input, not an afterthought.** Every table is shaped so that authorization can be expressed as a simple, indexable filter (`office_id` + role check), which keeps future RLS policies fast and easy to reason about. 7. **Denormalize only where reporting/query needs justify it.** A small number of convenience fields (e.g., `expenses.approved_by`) are intentionally duplicated from the generic approval engine to keep common reports and lists fast, while the full decision history remains in the audit tables as the source of truth. 8. **Soft-delete, never hard-delete**, on any record with real-world/business or financial meaning. Deletion is represented as a status change, preserving audit integrity. --- ## 2. RLS Strategy 1. **Office isolation, universally applied.** Every table's RLS policy includes a check that `office_id` matches the authenticated user's own `office_id` (looked up via `users.auth_user_id = auth.uid()`). This single pattern, applied consistently, is what makes multi-office data isolation automatic once multi-branch launches. 2. **Role-based action policies.** SELECT/INSERT/UPDATE/DELETE policies per table reference the `permissions` table (joined through the user's `role_id`) rather than hardcoding role names into each policy — keeps policies stable even as role permissions are tuned over time. 3. **Row ownership policies** for personal-scope data (e.g., an Employee can read/update their own `tasks` where `assigned_to = auth.uid()`-derived user id; can read their own `notifications`). 4. **Append-only tables locked down further.** `activity_logs` and `approval_actions` grant INSERT only (via trigger/Edge Function execution context), with no UPDATE or DELETE policy for any role, including Admin — this is enforced at the RLS layer, not just convention. 5. **Elevated operations via Edge Functions, not direct table grants.** Approval decisions, cross-module writes (e.g., approving an expense also writes an activity log and a notification) are executed through Edge Functions using the service role, so RLS on the underlying tables can stay strict for direct client access while these coordinated operations still succeed. 6. **Storage policies mirror table policies.** Supabase Storage bucket policies check the same role/office logic as the corresponding `documents`/`document_versions` RLS policies, so file access permissions never diverge from data access permissions. 7. **Settings table restricted tightly.** `company_settings` write access limited to Chairman/Vice Chairman/Admin roles only, per the approved permission matrix; Employees get read-only access to non-sensitive fields (e.g., currency, company name) if needed by the UI. --- ## 11. Storage Bucket Structure | Bucket | Purpose | Access Pattern | |---|---|---| | `documents` | Contracts, trade license, TIN, office agreements | Restricted to Chairman/Vice Chairman/Admin for write; broader read per document category if needed | | `bills` | Expense receipts and purchase invoices | Any authenticated user can upload (their own submissions); read scoped by role and office | | `avatars` | Staff/user profile photos | Self-upload by the staff member (if login-enabled) or Admin; public read within the office only | **Path convention:** `{office_id}/{module_key}/{record_id}/{version_number}_{file_name}` This mirrors the `document_versions.storage_path` structure, keeps files logically grouped per office (supporting future multi-branch storage segregation), and makes orphaned-file cleanup jobs straightforward — any storage object whose path doesn't correspond to a live `document_versions` row is a cleanup candidate. --- ## 12. Future Expansion Notes - **Multi-office rollout:** Add new rows to `offices`; assign new users/data going forward with the new `office_id`. Every RLS policy and index already accounts for this — no schema change needed. - **New modules adopting the approval engine:** Extend the allowed-value list on `approval_requests.module_key` — a single, low-risk change, no new table. - **New modules adopting the audit engine:** No schema change at all; `activity_logs.module_key` already accepts any module name — only a new trigger on the new module's table is needed. - **New statuses for any module:** Insert a row into `statuses` — zero migrations. - **Reporting growth:** Rather than pre-building speculative report tables now, the schema is indexed (Section 7) so that summary/materialized views (e.g., a monthly expense summary view) can be layered on top later without touching the underlying transactional tables — satisfying your requirement that reports can be built "without redesigning the database." - **HR/Payroll expansion:** `staff_directory` was deliberately kept lightweight so a future HR module can extend it (e.g., a linked `staff_employment_details` table) rather than replace it. - **CRM/Sales expansion:** Can reuse `documents`, `approval_requests`, `activity_logs`, and `notifications` engines directly — no modification to this schema required, only additive new tables. --- ## 13.
